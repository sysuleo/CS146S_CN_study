Warp Factory 示例：从 Issue 到 Pull Request 的完整工程流水线

原文：02: Issue to pull request

Warp 2026 约 12 分钟

总结

这个示例展示的不是“一个会写代码的 agent”，而是一整套把请求变成 PR 的工程流水线。

  • 入口有三个：Slack、Linear、GitHub；请求先经过 triage，需要时再生成 spec。
  • IMPLEMENT 负责改代码，REVIEW 用不同模型做审查，降低共享盲点。
  • 三种 runner 按阶段分配算力：读代码、跑构建、跑 macOS 构建各用各的机器。
  • GitHub 触发条件用 AND 组合：必须同时匹配 mention/assignment 和 routing label。
  • 所有配置都是文件：agents、automations、runners、scorers、skills 都可以读、可以改。
  • 最后一步仍然交给人：factory 只负责把 PR 准备好，合并由人决定。

原文逐段对照翻译

翻译说明：原文是 Warp Factory 的示例 README。以下按原文顺序翻译全部章节；目录结构、YAML 配置和命令保持原样。

This example is a complete engineering factory that takes requests from Slack, Linear, and GitHub through triage, specification when needed, and implementation. A separate agent reviews the changes before the factory hands the pull request to a human.

这个示例是一套完整的工程 factory：接收来自 Slack、Linear 和 GitHub 的请求，经过 triage、按需生成 spec、再进入 implementation。改完之后由另一个独立的 agent 做 review，最后把 PR 交给人类。

The example recreates the default agents and automations that Warp sets up for a new factory, as files you can read and edit. It also adds one custom agent.

这个示例把 Warp 为新 factory 默认创建的 agents 和 automations 还原成可读、可改的文件，并额外增加了一个 custom agent。

这个示例展示了什么

All five default agents (FOREMAN, TRIAGE, SPEC, IMPLEMENT, and REVIEW) appear, along with a CUSTOM agent for work the default agents don't cover. The triage and reviewer agents override the default model. The reviewer uses a different model than the implementer to reduce shared blind spots.

五个默认 agent（FOREMAN、TRIAGE、SPEC、IMPLEMENT、REVIEW）全部出现，另有一个 CUSTOM agent 处理默认 agent 覆盖不到的工作。triage 和 reviewer 覆盖了默认 model；reviewer 使用与 implementer 不同的模型，以减少共享盲点。

Three runners differ by size, image, and operating system, and each agent can select the one that suits its stage. See Runner configuration.

三个 runner 在规格、镜像和操作系统上各不相同，每个 agent 可以选择适合自己阶段的 runner。详见下面的 Runner configuration。

Requests come in from Slack, Linear, and GitHub, and a follow-up automation handles closed or merged pull requests. The directory structure below lists each automation's trigger.

请求来自 Slack、Linear 和 GitHub，另有一个后续 automation 处理已关闭或已合并的 PR。下面的目录结构列出了每个 automation 的触发方式。

The integrations list declares slack and linear, and the factory covers multiple repositories.

integrations 列表声明了 slack 和 linear，这个 factory 覆盖多个仓库。

Skills under skills/ are available to every agent. Skills under agents/<name>/skills/ are available only to that agent.

skills/ 下的 skill 对所有 agent 可用；agents/<name>/skills/ 下的 skill 只对该 agent 可用。

目录结构

目录结构：以下代码块保持原文；每个目录对应 factory 的一个部分：agents、automations、runners、scorers 和共享 skills。

factory.yaml
agents/
  foreman/agent.md       FOREMAN
  triage/agent.md        TRIAGE   (model: auto-efficient)
  spec/agent.md          SPEC
  implementer/agent.md   IMPLEMENT (runner: linux-build)
    skills/testing-standards/SKILL.md
  reviewer/agent.md      REVIEW   (model: auto-genius)
  mobile-build/agent.md  CUSTOM   (runner: macos-build)
automations/
  slack-app-mentions/    slack/app_mention
  slack-dms/             slack/message_dm
  linear-agent-sessions/ linear/agent_session_created
  github-mention-assign/ github issue+PR mentioned/assigned
  github-pr-closed-or-merged/  merged → complete work items
runners/
  linux-standard.yaml    4 vCPU / 8 GB, ubuntu:24.04
  linux-build.yaml       8 vCPU / 16 GB, golang:1.24-bookworm
  macos-build.yaml       6 vCPU / 14 GB, macos/aarch64
scorers/
  task-compliance/       scores implementer runs, selfImprovement on
  review-quality/        scores reviewer runs
skills/
  repository-conventions/SKILL.md   shared by every agent

Runner 配置

Each agent chooses its own compute. This factory uses three runners because its stages have different needs:

每个 agent 自己选择算力。这个 factory 使用三个 runner，因为不同阶段的需求不同：

linux-standard (4 vCPU / 8 GB, ubuntu:24.04) is the agentDefaults runner, which the foreman, triage, spec, and review agents inherit. These stages read code and write prose.

linux-standard（4 vCPU / 8 GB，ubuntu:24.04）是 agentDefaults 的 runner，foreman、triage、spec 和 review 都继承它。这些阶段主要是读代码、写文字。

linux-build (8 vCPU / 16 GB, golang:1.24-bookworm) runs implementation, which compiles code and runs tests. The image provides the toolchain, so use setupCommands only for what the image lacks, and write them defensively. A setup command that exits non-zero fails the whole sandbox.

linux-build（8 vCPU / 16 GB，golang:1.24-bookworm）运行 implementation，负责编译代码和跑测试。镜像已经提供工具链，所以 setupCommands 只补镜像缺少的东西，并且要写得防御性一些：任何一条 setup command 以非零退出，整个 sandbox 都会失败。

macos-build (6 vCPU / 14 GB, macos/aarch64) runs the mobile-build agent. macOS sandboxes are virtual machines, not containers, so this runner declares no dockerImage. It takes an optional mac.version instead and accepts only a fixed set of shapes. macOS is aarch64-only.

macos-build（6 vCPU / 14 GB，macos/aarch64）运行 mobile-build agent。macOS sandbox 是虚拟机而不是容器，所以这个 runner 不声明 dockerImage，而是接收可选的 mac.version，并且只接受一组固定规格。macOS 只有 aarch64。

Linux shapes must be powers of two. A runner named by an agent overrides the runner in agentDefaults.

Linux 规格必须是 2 的幂。agent 显式指定的 runner 会覆盖 agentDefaults 里的 runner。

GitHub 入口如何路由

The mention and assignment automation mirrors the default automation that Warp creates during setup. It watches only acme/api-service and acme/webapp, so GitHub mentions and assignments in acme/ios-app don't start work. GitHub intake for iOS work isn't set up.

mention 和 assignment automation 与 Warp 初始化时创建的默认 automation 一致。它只监听 acme/api-service 和 acme/webapp，所以 acme/ios-app 里的 GitHub mention 和 assignment 不会启动任务；iOS 工作的 GitHub 入口没有配置。

Filter keys combine with AND. Each trigger combines a mention or assignment filter with a label filter:

Filter 的各个 key 用 AND 组合。每个 trigger 都是“mention 或 assignment 条件”再加“label 条件”：

mentioned: [warp, warp-factory] and assignees: [warp, warp-factory] restrict the trigger to the GitHub handles Warp Factories answers to. The current handle is warp. The earlier handle, warp-factory, still matches. Both are product constants, not placeholders. Without the mentioned key, issue_mentioned fires when anyone is @-mentioned in the repositories.

mentioned: [warp, warp-factory] 和 assignees: [warp, warp-factory] 把 trigger 限制在 Warp Factories 会响应的 GitHub handle 上。当前 handle 是 warp，早期的 warp-factory 仍然匹配。两者都是产品常量，不是占位符。如果不写 mentioned，那么仓库里任何人被 @ 提到都会触发 issue_mentioned。

labels: ["factory:Acme"] is the factory's routing label, factory:<alias>. Because filters combine with AND, the label must be on the issue or pull request before a mention or assignment can trigger the factory. A @warp mention on an unlabeled item is silently dropped, so apply the label when you open the item or before the first mention. After that, the foreman keeps the label on everything it touches, so later mentions and assignments keep matching.

labels: ["factory:Acme"] 是这个 factory 的路由 label，格式是 factory:<alias>。因为 filter 用 AND 组合，issue 或 PR 上必须先有这个 label，mention 或 assignment 才能触发 factory。未打 label 的条目上写 @warp 会被静默丢弃，所以要在创建条目时或第一次 mention 之前打上 label。之后 foreman 会一直给它接触的所有东西保留这个 label，后续 mention 和 assignment 才能继续匹配。

The closed-or-merged follow-up automation watches acme/api-service, acme/webapp, and acme/ios-app. The mobile-build agent's pull requests land in acme/ios-app and need the same follow-up when they are closed or merged. The same routing label limits the automation to factory pull requests instead of every merge in the repository.

closed-or-merged 后续 automation 监听 acme/api-service、acme/webapp 和 acme/ios-app。mobile-build agent 的 PR 会落在 acme/ios-app，关闭或合并时也需要同样的后续处理。它同样用 routing label 把 automation 限制在 factory 的 PR 上，而不是仓库里的每一次 merge。

Widen these filters carefully. If you drop the labels key from the mention triggers, any @warp mention starts work. If you also drop mentioned, the trigger fires on every mention of anyone.

放宽这些 filter 时要小心。如果去掉 mention trigger 里的 labels，任何 @warp mention 都会启动任务；如果连 mentioned 也去掉，那么任何人被 mention 都会触发。

定制这个示例

1. Replace acme/api-service and acme/webapp with repositories that your installation can access. They appear in factory.yaml and in both GitHub automations. The repository name api-service also appears in the linux-build setup command.

1. 把 acme/api-service 和 acme/webapp 换成你的安装可以访问的仓库。它们出现在 factory.yaml 和两个 GitHub automations 里；仓库名 api-service 还出现在 linux-build 的 setup command 里。

2. Replace acme/ios-app with a repository that your installation can access. It appears in factory.yaml, agents/foreman/agent.md, agents/mobile-build/agent.md, and the github-pr-closed-or-merged automation, but not in the github-mention-assign automation.

2. 把 acme/ios-app 换成你的安装可以访问的仓库。它出现在 factory.yaml、agents/foreman/agent.md、agents/mobile-build/agent.md 和 github-pr-closed-or-merged automation 里，但不在 github-mention-assign automation 里。

3. If you don't have macOS work, delete agents/mobile-build/ and runners/macos-build.yaml, and remove the ios-app entry from factory.yaml and from the github-pr-closed-or-merged automation. Make all of these changes together.

3. 如果没有 macOS 相关工作，删除 agents/mobile-build/ 和 runners/macos-build.yaml，并从 factory.yaml 和 github-pr-closed-or-merged automation 里移除 ios-app。这些改动要一起做。

4. Connect Slack to your Warp team.

4. 把 Slack 连接到你的 Warp team。

5. Connect Linear to your Warp team. The integrations list declares which integrations the factory uses, but doesn't connect them.

5. 把 Linear 连接到你的 Warp team。integrations 列表只声明 factory 使用哪些 integration，并不会替你完成连接。

6. Replace the two skill stubs, skills/repository-conventions/SKILL.md and agents/implementer/skills/testing-standards/SKILL.md, with your real conventions.

6. 把两个 skill 占位文件 skills/repository-conventions/SKILL.md 和 agents/implementer/skills/testing-standards/SKILL.md 换成你团队真正的约定。

7. Optionally, narrow intake. Filters combine with AND, and an absent field matches everything. For example, to route only one Linear team, add a filter to the trigger:

7. 可选：收窄入口。Filter 用 AND 组合，不写的字段等于匹配所有。比如只路由一个 Linear team，可以给 trigger 加 filter：

triggers:
  - provider: linear
    event: agent_session_created
    filter:
      teams: [Platform]

The teams and projects filters take plain lists of names. Warp resolves the names against Linear when you apply the definition, so add them only after you connect Linear. Otherwise, applying the definition fails on the unresolved name.

teams 和 projects filter 接收简单的名称列表。Warp 在应用定义时会拿这些名字去 Linear 里解析，所以要先连接 Linear 再添加；否则应用定义时会因为名字无法解析而失败。

The agent_session_created event also accepts labels, keywords, and creator_ids. It rejects a states filter. Use states with issue_state_changed instead.

agent_session_created 事件还接受 labels、keywords 和 creator_ids；它不接受 states filter。需要按状态过滤时，改用 issue_state_changed。

用 Jira 替代 Linear

A factory can attach Linear or Jira, but not both. To use Jira instead of Linear:

一个 factory 可以接 Linear 或 Jira，但不能同时接两者。要用 Jira 替代 Linear：

1. Change the integration in factory.yaml to - type: jira.

1. 把 factory.yaml 里的 integration 改成 - type: jira。

2. Replace automations/linear-agent-sessions with an automation that uses the jira provider and the agent_session_created event. Jira filters use project_keys instead of team names.

2. 把 automations/linear-agent-sessions 换成使用 jira provider 和 agent_session_created 事件的 automation。Jira filter 使用 project_keys，不是 team 名称。

3. Update the Linear references in the triage prompt.

3. 更新 triage prompt 里所有 Linear 相关的引用。

配置更多 trigger

Intake is defined by triggers, so you can point a factory at other kinds of events without changing its agents. For example, to review pull requests that humans open, and not only factory pull requests, route them directly to the reviewer with the automation's agent: field:

入口由 trigger 定义，所以不用改 agents，就能让 factory 处理其他类型的事件。比如要 review 人类开的 PR，而不只是 factory 自己的 PR，可以用 automation 的 agent: 字段直接路由给 reviewer：

agent: reviewer
triggers:
  - provider: github
    event: pull_request_opened
    filter:
      repos: [acme/api-service]
      base_branches: [main]
      labels:
        not_in: [wip]

The pull_request_synchronized event fires on every push to an open pull request, and pull_request_opened fires for drafts too, so an opt-out label is the practical way to control volume. An automation fires once per delivery, even when several of its triggers match the same event.

pull_request_synchronized 会在打开的 PR 每次 push 时触发，pull_request_opened 连 draft 也会触发，所以用一个 opt-out label 是控制触发量的实用办法。一个 automation 每次 delivery 只触发一次，即使多个 trigger 同时匹配同一个事件。

For recurring work that doesn't start from a human request, such as a dependency sweep, see the cron automation in 06-common-automations.

对于不来自人类请求的周期性工作，比如依赖巡检，可以参考 06-common-automations 里的 cron automation。

学习者视角

关键收获

  1. Factory 的核心是流水线，不是单个 agent。 triage、spec、implement、review 各自有输入输出，最后交给人合并。
  2. 模型反转是默认设计。 reviewer 和 implementer 用不同模型，直接针对共享盲点。
  3. 算力按阶段分配。 读代码用 4 vCPU，编译用 8 vCPU，macOS 构建用虚拟机；没有必要所有阶段都上大机器。
  4. 触发条件要收窄。 mention、assignment、label 用 AND 组合，避免任何一条消息都启动任务。
  5. 配置即代码。 agents、automations、runners、scorers 都能进版本控制，factory 的行为才可复现、可审计。

放回课程里看

这篇是 Week 9 的“software factory”落地样例：它把 Week 8 的后台 agent、Week 6 的 review agent、Week 4 的 AGENTS.md/skills 组合成一条从 issue 到 PR 的流水线。和 OpenInspect 相比，Warp 更强调多入口、多 runner 和可配置的路由；和 WarpBench 搭配看，可以理解“factory 配置”如何进一步被 benchmark 优化。

一个反直觉点

很多人以为 agent 越多越好。这个示例的重点恰恰是边界：repos 只监听两个、iOS 入口不配置、mention 必须带 label、review 用不同模型。限制入口和模型重叠，比继续加 agent 更能提升可靠性。

拓展

思考题

  1. 如果把 triage 和 spec 合并成一个 agent，会失去什么？
  2. 为什么 reviewer 要和 implementer 用不同模型？换模型能解决哪些盲点，不能解决哪些？
  3. 你的团队里，哪些阶段值得用 8 vCPU，哪些阶段 4 vCPU 就够？
  4. 如果去掉 routing label，会发生什么？你会怎么设计一个更安全的默认值？

练习

为你自己的仓库画一条最小的 issue-to-PR factory：

  • 入口来自哪里（Slack / Linear / GitHub）；
  • 需要哪几个 agent（triage、spec、implement、review）；
  • 每个 agent 用哪个 runner；
  • reviewer 用哪个不同模型；
  • 哪些 label 或 filter 用来限制触发范围；
  • 哪一步必须由人做。
